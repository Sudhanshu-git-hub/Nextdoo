# Security verification and release prerequisites

This repository has bounded ASVS L2-oriented security evidence, not an ASVS certification or a statement that a deployment is secure. The current [control matrix](docs/M8_i8_SECURITY_CONTROL_MATRIX.md) uses the requested ASVS 4.0.3 V1–V14 categories. [OWASP's releases](https://github.com/OWASP/ASVS/releases) include ASVS 5.0 with different chapter numbering. The matrix deliberately distinguishes implemented behavior from incomplete and external controls.

## Local and CI checks

Run `pnpm security:scan`. It needs only the locked local TypeScript package, Node and Git; it makes no network request and uploads no repository content. It examines tracked working-tree files plus non-ignored untracked files returned by Git. Tracked ignored files are included. It does not scan commit history, `.git` internals, ignored developer env files, or binary assets. It rejects tracked `.env` variants other than `.env.example`, even when binary. Symlinks and unreadable listed files fail closed. Run on a clean checkout in CI; platform push protection remains a separate repository setting.

The secret rules recognize private-key headers, GitHub/provider/cloud token formats, JWT-like values, credential-bearing database/mail URLs, uppercase configuration assignments, and credential-named literal/fallback assignments in TypeScript/JavaScript. No entropy-only heuristic is used. Unknown token formats, arbitrary encodings, constructed strings, encrypted archives and deleted Git history are outside this bounded scan; passing it is not proof that all secrets are absent.

The TypeScript AST guard checks direct dynamic code execution, imported child-process shell execution (including named aliases/namespaces), disabled TLS verification, `shell: true`, HTML sinks and dynamic `sql.raw`. It permits direct `renderDescription` HTML calls, whose sanitizer implementation and malicious-input tests remain a required review boundary. Dynamic SQL from reviewed finite enum/identifier maps has explicit file-pinned exceptions. This is **bounded static security coverage**, not general dataflow/taint analysis or a complete SAST assessment. Aliasing/reassignment/reflection can evade a syntactic guard; normal code review and behavioral tests remain necessary.

Findings print JSON with only file, line and rule; neither source snippets nor secret values are printed. Exit 0 means no prohibited findings, 1 means findings, 2 means the scan could not complete. Avoid logging raw scanner internals when troubleshooting.

`security-allowlist.json` contains exact file/rule/SHA-256 fingerprints and a review reason. There are no wildcard path exceptions and no blanket test-directory exemption. Secret exceptions bind the exact match; static exceptions bind the complete normalized source file so upstream changes demand review. Duplicates, malformed exceptions and stale entries fail the scan. Existing exceptions cover synthetic local/CI credentials, the explicitly published browser-test VAPID key, and reviewed parameterized-query/DDL test boundaries. None authorize real deployment credentials. Do not automatically baseline new findings: inspect the source privately, rotate/revoke any genuine credential, and remove it before considering an exception. A fingerprint is not encryption and is only appropriate for already-public safe fixtures.

`pnpm verify` starts with this gate. CI runs it immediately after frozen-lockfile installation, then retains dependency audit, migrations twice, lint, types, full coverage, build, logical backup/restore, real ClamAV/EICAR, and the complete browser suite. Tests construct synthetic scanner values, verify redacted CLI failures and ignored-but-tracked env detection, and exercise exception scope/staleness. No production credentials are required.

## Runtime boundaries changed in M8-i8

OAuth state consumption is an atomic conditional DELETE RETURNING, restricted to the authenticated browser account and its expiry. A concurrent callback cannot exchange the same state twice, and another account cannot consume it. An expired or revoked session must sign in and restart authorization; callbacks continue to use fixed Settings destinations and generic failures. The provider flow still uses PKCE and existing token sealing/resealing. This does not claim live Google acceptance.

Attachment uploads retain the existing byte cap, signed token and owner checks. After receiving bytes, the final storage write rechecks ownership/deletion/completion under a row lock. Completion and deletion share that lock, preventing an already-started upload from replacing CLEAN bytes or recreating deleted storage. The scanner architecture and clean-only download gate are preserved. A database lock is not held while receiving the network body.

Structured logging normalizes punctuation/case in credential field names and redacts nested token/password/key/secret aliases, connection URLs, recovery codes and PKCE verifiers. Safe request IDs, routes and status diagnostics remain available. Unknown server errors still return generic problem responses; request bodies, provider errors and credentials must never become free-form log messages.

## Release-readiness register

| Classification | Current evidence / remaining requirement |
|---|---|
| A. APPLICATION-CODE COMPLETE | Bounded mapped owner checks, session revocation, reset/MFA transitions, mutation replay/version checks, corrected OAuth state consumption/account binding, corrected attachment finalization race, credential-field redaction, deterministic secret/static gate, nonce CSP/header and HTTP authorization regressions. Final counts and immutable CI link belong in the delivery report. |
| B. APPLICATION-CODE PARTIAL | No breached-password screening or distinct idle-session timeout; scrypt fallback remains; no independent comprehensive SAST/ASVS/pentest assessment. General throttles are per process, JSON buffering has no universal application byte cap, and attachment MIME declarations are not file-magic validation. Google webhook ingress still uses the connection identifier rather than a dedicated channel secret and live header verification is unresolved: this is a release blocker for exposed production Calendar webhook ingress. No production-ready claim follows from fixture webhook tests. |
| C. EXTERNAL / DEPLOYMENT DEPENDENCY | Trusted ingress must constrain Host/forwarded headers, rate-limit across instances, enforce request byte/time/concurrency budgets, and terminate HTTPS. Validate DB TLS, CSP behavior, cookie flags, ClamAV signatures/availability/resource limits, scan handling for encrypted/oversized archives, storage permissions/symlink exclusion, and local-object-store durability/backup. S3 configuration fields do not prove an S3 storage adapter or production bucket is active. |
| C. EXTERNAL / DEPLOYMENT DEPENDENCY | Live Google OAuth/webhook acceptance, SMTP delivery, deployed VAPID push, billing activation, managed secret injection/rotation, least-privilege DB/runtime identities, encrypted backups/PITR/object-byte restore, deletion-window backup/legal policy, RTO/RPO, rollback rehearsal, alerting, uptime/SLO windows and named on-call procedures need actual deployment/provider evidence. CI restore is logical synthetic data only. |
| D. DEFERRED / FUTURE | Third-party security assessment and broad taint-analysis tooling; dedicated Google webhook channel credentials/live acceptance; distributed abuse infrastructure; production container/image build and scanning (no current Docker/image target); platform push-protection configuration; stronger password/session policy. These must be explicitly reviewed before the applicable release. |
| E. NOT APPLICABLE | Native-client privilege controls, marketplace/plugin execution and team-role matrices for the present personal web application. These require a fresh assessment if those products are introduced. |

No historical migrations were changed. No new provider, storage system, product feature or deployment was introduced by this milestone. A code milestone may be complete while these production release prerequisites remain open.
